`tamper/`, commit `d2d37b40…`.

**The matrix** (`tamper/tamper-matrix-1115Z.log`). One byte flipped in a pinned file → `shasum -a 256 -c
SHA256SUMS` exit 1, the file named. Which layer catches it after that depends on whether a script *reads*
the file:

- `chit/jwks.json`, one base64url character of `keys[0].x`: that file is an input, and the issuer script
  exits **1** — 2 FAIL, 12 OK (`JWKS key == receipt-embedded key`, `… == history entry key`).
- the pinned receipt's signed `issuer_history.hash` (a targeted re-encode, not a byte flip): the issuer
  script exits **1** — 2 FAIL, 12 OK (`served bytes hash to the pinned value`; `the pinned value is also the
  JCS hash`).
- `chit/preimage.body.json` and `chit/issuer-history.json`: the script that uses each one re-fetches and
  overwrites it, so a live run passes (exit 0) and only the checksum catches the flip.

**Halt or log.** Log-and-continue: `check()` counts failures and prints the whole list, then exits 1. Both
tampered runs printed 12 OK + 2 FAIL + the result line.

**The NOTE.** It is not a check that never fired — it is the one finding the script prints: `the signed
payload names the hash algorithm: false`. `hash_alg` and the canonicalization rule live in the envelope
(`issuer_signature.hash_alg`) and the response headers, outside the JWS. It would not catch a rotation.
Rotation is caught by the other script's checks: two snapshot lines (`served bytes hash to the pinned
value` and `the pinned value is also the JCS hash`) and `document seq/version == the values the receipt
pinned`. Rehearsed in `tamper/rotation-rehearsal-1115Z.log` against a document with a second entry and
`version/seq 2`: 6 FAIL, exit 1 — those three lines, plus three on its signed payload, which we cannot
re-sign. Bound: both fire
only against a receipt issued *before* the change, and they catch any change to the document, not rotation
as such; a receipt issued after a rotation pins the new document and passes, and no real rotation has been
observed.

**And the live negative case.** Refreshing `chit/receipt.format-json.body` failed the checksum independently
of any tamper. `GET /receipt/<id>?format=json` re-signed on each of five fresh reads: the JWS header and
payload byte-identical across the pinned body and all five, the ES256 signature different every time, and
the `coverage` object's signature the same way (`tamper/segments.mjs`, `segments-1115Z.log`). `GET
/receipt/<id>/preimage` is the opposite: two reads seconds apart, both `946e2652…`, 2,288 bytes — the pair
c94912 reported at 3 h 21 min, which did not include the receipt body. So the `?format=json` body cannot be
pinned by digest; the stable objects are the preimage and the JWS payload.
